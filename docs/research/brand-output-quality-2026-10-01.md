# Logopia 브랜드 아웃풋 품질 개선 연구

조사일: 2026-10-01. 기존 [후보 스킬·플러그인 조사](logo-brand-skills-plugins-2026-10-01.md)의 고정 커밋을 다시 확인하고, Google·IBM·Atlassian의 공식 브랜드 자료와 Adobe·W3C의 원문을 추가로 읽었습니다. 외부 스킬 설치, 계정 연결, 유료 API 호출은 이 연구에서 실행하지 않았습니다.

**결론: 브랜드 맥락과 검증 절차는 흡수하되, 외부 스킬의 미학을 기본값으로 흡수하지 않습니다.** 실제 제품에서 쓰는 로고 원본을 먼저 만들고, 색상·글자·형태가 그 상태에서 성립하는지 확인해야 합니다. 브랜드 보드나 시네마틱 목업은 그 이후의 선택적 응용물입니다.

후속 구현과 실제 6장 비교는 [품질 검증 기록](../qa/brand-output-quality-2026-10-01/README.md)에 있습니다. 아래 연구의 가설·제안과 구분하여, 모든 원본과 제한된 블라인드 관찰 및 미해결 문제를 보존했습니다.

## 문제와 증거의 구분

- **사용자 보고:** 특정 실패 파일은 제시되지 않았지만, 일반적으로 결과의 질이 낮고 색 조합·브랜드 적합성이 부족합니다. 베이지 배경, 게임 속 산업 회사 같은 합성 로고, 인위적인 시네마틱 연출이 나오며 실제 제품에 바로 쓰기 어렵다는 추가 피드백이 있습니다.
- **원문에서 관측:** Taste `brandkit`은 브랜드 의미·응용물 일관성을 다루면서도 premium, minimal, cinematic과 어두운 보드, 재질·이미지 연출을 반복적으로 권장합니다. 이를 전체 로고 생성의 기본값으로 합치면 사용자 피드백과 충돌합니다. [고정 원문](https://github.com/Leonxlnx/taste-skill/blob/ce26fc25c0e5e8cab638f883de62d9a86ee5e45b/skills/brandkit/SKILL.md)
- **원인 가설:** 브랜드 정보가 구체적인 조형 제약으로 연결되지 않고, 분위기·기하 트릭·목업 연출이 실제 사용 적합성을 대신하는 흐름이 실패를 반복시킬 수 있습니다. 이는 아직 기존 생성물의 체계적인 분석으로 입증된 원인이 아닙니다.
- **효과 미확인:** 아래 지침은 조사에 근거한 개선안입니다. 문서의 분량, 프롬프트의 정교함, 자동 검사 통과만으로 생성 품질이 좋아졌다고 주장하지 않습니다. 같은 브리프를 사용한 실제 생성·비교가 필요합니다.

## 실무 원칙 6개

### 1. 브랜드 의미를 조형 결정으로 번역하되 은유를 강제하지 않습니다

**관측:** `brand-identity`는 브랜드 의도에서 로고 방향과 피할 요소를 도출합니다. Google의 공식 리디자인 기록도 기존 브랜드 성격과 실제 기기·화면 제약을 함께 출발점으로 삼습니다. [Brand Building Skills](https://github.com/arnabbagxd/Brand-building-skills/blob/4a0a8b5b7a0f64bf0fc551978a18a591670a5223/skills/brand-identity/SKILL.md), [Google](https://design.google/library/evolving-google-identity)

**적용 제안:** 대상, 제공 가치, 원하는 인상, 피할 인상, 쓰일 장소를 기존 입력에서 추출합니다. 각 후보에는 “이 브랜드 정보 때문에 이 형태·색·글자를 택했다”는 짧은 근거가 있어야 합니다. 미확인 타깃·경쟁사 사실을 만들어내지 않고 가정으로 남깁니다.

- 워드마크, 직접적인 심볼, 추상 심볼, 캐릭터, 심볼+워드마크 중 사용 환경과 요청에 맞는 형식을 선택합니다. 숨은 의미가 없는 단정한 워드마크도 유효합니다.
- 업종만 보고 방패·잎·스파클·궤도·번개를 자동 선택하지 않습니다. 특정 모티프는 브랜드 근거가 있을 때 사용합니다.
- 모노그램+은유 결합, 사선 절개, 겹친 이니셜, 음각 트릭을 의무화하지 않습니다. 합쳐야만 독창적인 것이 아닙니다.
- 후보 간 차이는 색만 바꾸는 것이 아니라 표정, 실루엣, 글자 성격, 의미 전달 방식처럼 비교 가능한 디자인 결정이어야 합니다.

**실패 판정:** 설명을 읽어야만 의미가 보이거나, 브랜드 이름을 다른 이름으로 바꿔도 똑같이 그럴듯한 근거만 남는 경우 재검토합니다. 이는 법적인 독창성·상표 검증을 대신하지 않습니다.

### 2. 로고 원본을 실제 사용 크기와 배경에서 먼저 검증합니다

**관측:** Atlassian은 실제 제품용 심볼과 워드마크 조합, 배경에 맞는 색상 변형을 구분하고 그림자·복잡한 배경을 제한합니다. 해당 규칙은 Atlassian의 브랜드 규칙이며 모든 브랜드의 의무 규격은 아닙니다. [Atlassian 로고 가이드](https://atlassian.design/foundations/logos)

**적용 제안:** 일반적인 새 로고 요청의 기본 산출물은 장식이 없는 원본 로고입니다. 투명도가 필요하면 실제 알파 채널을 검증합니다. 불투명 시안에는 지정된 단색 배경을 사용하되 배경이 로고의 일부인지 미리보기용인지 분명히 합니다.

- 베이지·아이보리 보드, 종이 질감, 금속 엠보싱, 3D 제품 촬영, 조명·렌즈·시네마틱 연출은 무지시 기본값에서 제외합니다.
- 실제로 쓰일 헤더·로그인 화면·아이콘 등에서 테스트합니다. 넓은 목업 중앙에 크게 올린 모습만으로 승인하지 않습니다.
- 심볼+텍스트는 심볼의 시각 무게, 이름의 읽힘, 둘 사이 간격과 정렬을 함께 평가합니다. 심볼에 맞춰 이름을 지나치게 작게 만들지 않습니다.
- 사용자에게 명시된 playful, 다색 IP, 3D 앱 아이콘, 게임 타이틀 표현은 유지합니다. 위 기본값은 표현을 획일적인 기업용 기하 로고로 바꾸는 명령이 아닙니다.

**실패 판정:** 배경·빛·목업을 제거하면 형태나 글자가 성립하지 않는 경우, 요청하지 않은 판타지 기업 배지·복잡한 합성 문양이 나온 경우 원본 단계에서 수정합니다.

### 3. 색 조화는 역할과 관계로 설계합니다

**관측:** Google은 워드마크의 떨어진 색과 작은 G의 맞닿는 색이 다르게 보이므로 색을 보정했다고 설명합니다. IBM은 명도 단계, 색상군, 배경 조합을 명시합니다. 서로 다른 두 브랜드의 운영 방식이며 한쪽 팔레트를 일반 정답으로 가져올 근거는 아닙니다. [Google 색상 기록](https://design.google/library/evolving-google-identity), [IBM 색상 가이드](https://www.ibm.com/design/language/color/)

**적용 제안:** 색마다 HEX와 함께 역할, 적용 위치, 허용 배경, 의도한 시각 비중을 적습니다. 비중은 넓은 면·보조 면·작은 포인트처럼 설명할 수 있으며 정확한 면적을 측정하지 않았다면 수치로 단정하지 않습니다.

- **명도:** 맞닿은 면이나 중요한 내부 디테일이 합쳐져 보이는지 확인합니다. 다른 색상 이름이어도 명도가 비슷하면 형태가 묻힐 수 있습니다.
- **채도:** 모든 요소가 동시에 주의를 끌지 않도록 역할별 강약을 봅니다. 다색 캐릭터의 선명한 색은 정당한 선택이며 채도를 일괄 낮추지 않습니다.
- **색상 관계:** 유사색·보색 같은 분류는 출발점일 뿐 품질 증거가 아닙니다. 실제 인접 관계와 배경에서 다시 확인합니다.
- **면적:** 작은 포인트에서 좋은 색이 큰 배경 면에서 같은 효과를 내는지 별도로 봅니다. 캐릭터의 신체색·포인트·배경·텍스트를 같은 역할로 취급하지 않습니다.
- **배경:** 밝음·어두움 변형이 필요한 경우 각각 검토합니다. 기존 로고를 모든 배경에 자동 재색칠하는 방식은 피합니다.
- **실측과 의도:** 지정 HEX와 이미지의 측정 색을 구분합니다. 안티앨리어싱·그림자 픽셀을 새 브랜드 색으로 추가하지 않습니다.

고정 60/30/10, 색 두 개 이하, 항상 보색·저채도·검정 배경 같은 보편 규칙은 두지 않습니다. 색이 많다는 이유만으로 사용자가 요청한 다색 브랜드를 실패 처리하지 않습니다.

**검증의 범위:** WCAG 2.2의 최소 텍스트 대비 기준에는 로고·브랜드명에 대한 예외가 있습니다. 현재 해설은 이를 브랜드 정체성상 필요한 색상 제약과 연결하며, 표시 과정에서 임의로 대비를 낮춘 경우까지 면제하지 않습니다. 링크·버튼 역할의 로고에는 충분한 대비의 변형이나 동등한 컨트롤도 고려합니다. 주변 본문·버튼 텍스트를 로고와 함께 면제하지 않습니다. 대비 수치는 특정 글자/배경 쌍의 가독성 검사에 쓰고, “색 조화 점수”나 브랜드 적합성의 증거로 쓰지 않습니다. [W3C SC 1.4.3 해설](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

### 4. 로고 레터링과 실제 제품 폰트를 분리하고 한글 혼용을 직접 확인합니다

**관측:** Adobe는 한글·라틴의 시각 크기·무게중심·기준선 차이와 커닝/트래킹의 차이를 설명합니다. 조화로운 페어링과 의도적인 대비를 모두 허용합니다. W3C의 한국어 조판 초안도 한글 고정폭·비례폭을 구분합니다. [Adobe 페어링 기본](https://helpx.adobe.com/kr/fonts/using/basics-of-font-pairing.html), [Adobe 다국어 섞어짜기](https://helpx.adobe.com/kr/fonts/using/multiscript-typesetting.html), [W3C KLREQ, 2026-03-21 초안](https://www.w3.org/TR/2026/DNOTE-klreq-20260321/)

**적용 제안:** 워드마크 레터링, 제목용 서체, 본문/UI용 서체를 역할로 구분합니다. 같은 패밀리를 사용할 수도 있고 다른 패밀리를 쓸 수도 있습니다. 항상 서체 두 종이나 세리프+산세리프 조합을 만들 필요는 없습니다.

- 정확한 브랜드명의 철자·대소문자·한글 음절·구두점을 기준으로 검토합니다. 이미지가 그럴듯한 단어처럼 보여도 다른 글자라면 수정합니다.
- 폰트 이름을 추천할 때 실제 출처·라이선스·필요한 문자 지원을 확인합니다. 추천 폰트와 이미지 모델이 생성한 커스텀 레터링이 동일하다고 주장하지 않습니다.
- 한글·영문 혼용은 실제 이름을 함께 보며 크기, 획의 시각 무게, 기준선, 글자쌍의 빈 공간, 전체 자간 리듬을 확인합니다.
- 누락 글리프나 임의 폴백을 완성으로 취급하지 않습니다. “영문 105%” 같은 특정 사례의 보정값을 보편 상수로 저장하지 않습니다.
- 장식용 레터링에 적합한 글꼴이 긴 본문에도 적합하다고 자동 판단하지 않습니다. Adobe Source Serif의 크기별 변형은 사용 크기에 따라 비례·간격이 달라지는 실제 사례입니다. [Source Serif 4](https://fonts.adobe.com/fonts/source-serif-4-small-text)

**실패 판정:** 이름이 틀리거나 한글이 깨진 경우, 같은 로고 안에서 서로 다른 폰트처럼 글자 무게가 튀는 경우, 심볼과 글자가 경쟁하거나 이름이 읽히지 않는 경우에는 전달 가능한 워드마크로 승인하지 않습니다.

### 5. 수학적 일치보다 보이는 균형을 검증하고 가짜 구성도를 만들지 않습니다

**관측:** IBM의 정상·역상 로고는 보기에는 비슷한 획 무게가 되도록 실제 줄 두께와 내부 끝부분이 다릅니다. Google G도 작은 크기용 시각 무게와 곡선 접점의 광학 조정을 설명합니다. [IBM 8-bar](https://www.ibm.com/design/language/ibm-logos/8-bar/), [Google G](https://design.google/library/evolving-google-identity)

**적용 제안:** 도형 중심·동일 간격·같은 획 두께만으로 균형을 선언하지 않습니다. 실제 크기의 검은 덩어리와 빈 공간, 곡선 접합부, 카운터, 좌우 무게, 심볼과 이름 사이 여백을 봅니다. 최소 사용 크기는 확인한 환경에서만 기록합니다.

구성도는 실제 벡터 경로나 측정 가능한 원본 구조가 있을 때만 제공합니다. 래스터 로고에 임의의 원·황금비·그리드를 덧그린 후 실제 제작 원리라고 주장하지 않습니다. 아이디어 설명이 필요하면 조형 의도를 문장이나 명확히 표시한 개념 스케치로 설명합니다. 이는 공식 출처의 요구가 아니라 Logopia의 증거 정직성을 위한 제안입니다.

### 6. 확정 원본을 보존한 응용물을 만들고 결과의 종류를 명확히 합니다

**관측:** `brandkit`의 기본 결과는 한 장의 브랜드 키트 이미지입니다. Atlassian은 실제 재사용할 수 있도록 심볼·워드마크 조합과 색상·배치 변형을 별도 자산으로 제공합니다. [brandkit](https://github.com/Leonxlnx/taste-skill/blob/ce26fc25c0e5e8cab638f883de62d9a86ee5e45b/skills/brandkit/SKILL.md), [Atlassian](https://atlassian.design/foundations/logos)

**적용 제안:** 확정된 로고 파일을 브랜드 보드에서 재사용합니다. HTML 보드의 색상값·이름·폰트 설명은 텍스트로 배치하고, 생성한 목업은 응용 예시로 표시합니다. 목업 속 로고가 원본과 같은지 확인하기 전에는 납품용 변형으로 등록하지 않습니다.

원본 로고, 생성 응용 이미지, 추천 폰트, 실제 사용 폰트, 벡터 변환 결과를 구분합니다. 브랜드 가이드에는 사용자가 받은 파일·검증한 배경·사용 크기·색상 역할을 먼저 적고 제작 프롬프트나 측정 로그는 별도 기록으로 연결합니다.

## Recraft의 선택형 범위와 연결 없는 경로

현재 공식 원격 서버는 `https://mcp.recraft.ai/mcp`이며 Streamable HTTP와 OAuth 2.0을 사용합니다. 래스터/벡터 생성, 래스터 벡터화, 수정, 배경 처리 등을 제공하며 Recraft Studio와 구독 크레딧을 공유합니다. 원격 MCP에 API 키를 직접 넘기는 절차가 필수인 것은 아닙니다. [공식 원격 MCP 문서](https://www.recraft.ai/docs/mcp-reference/remote-server)

- **연결된 경우의 제안:** 사용자가 벡터 결과를 원하고 해당 기능이 사용 가능할 때 선택 원본을 기준으로 SVG를 만들 수 있습니다. 변환 뒤 글자·실루엣·내부 빈 공간·색·작은 크기를 원본과 비교합니다. 변환 호출의 성공이 디자인 보존의 증거는 아닙니다.
- **연결되지 않은 경우:** 기존 네이티브 이미지 생성으로 PNG 원본·미리보기·가이드를 제공합니다. SVG가 필요하다는 요구는 미충족으로 명시합니다. 내장 PNG를 감싼 SVG나 확장자 변경을 실제 벡터로 부르지 않습니다.
- **범위:** 이 연구는 Recraft 도구 호출·인증·변환 품질을 시험하지 않았습니다. SDK나 별도 생성 엔진 구현을 제안하지 않으며, 기본적인 브랜드·색·타입 품질 개선을 Recraft 연결에 의존시키지 않습니다.

## 실제 개선을 확인할 작은 생성 실험

아래는 **제안하는 평가 설계**이며 아직 완료된 실험 결과가 아닙니다. 사용자가 특정 실패 파일을 제시하지 않았으므로 새 비교 샘플을 이전 결과의 직접 재현이라고 표현해서는 안 됩니다.

1. **다른 요구를 대표하는 브리프를 고정합니다.** 제품용 심볼, 한글/영문 워드마크 또는 조합형, 다색 playful IP를 포함합니다. 타깃·성격·피할 인상·정확한 이름·사용 배경·최소 크기는 각 브리프에서 고정합니다. 장식 억제가 표현력 억제로 변하는지 확인할 사례도 포함합니다.
2. **이전·개선 지침의 실제 프롬프트와 생성물을 보존합니다.** 가능한 한 같은 제공자·설정·요구사항을 사용하고 순서를 섞어 비교합니다. 모델 버전이나 seed가 노출되지 않으면 불명으로 적습니다. 한 번의 생성 차이를 지침의 인과 효과로 단정하지 않습니다.
3. **같은 표면에서 비교합니다.** 원본, 실제 작은 크기, 필요한 배경, 헤더 또는 아이콘 사용 장면을 나란히 봅니다. 이전은 평면 이미지, 개선안은 화려한 목업으로 보여주는 비교는 피합니다.
4. **관찰을 항목별로 남깁니다.** 브랜드 적합성, 철자, 형태 식별, 심볼·글자 균형, 인접 색/배경 구별, 요청하지 않은 재질·빛·배경, 바로 사용 가능한 파일 여부를 기록합니다. 가독성 실패를 다른 항목 점수의 평균으로 상쇄하지 않습니다.
5. **통과 범위를 좁게 보고합니다.** 어느 브리프에서 어떤 결함이 줄었는지, 남은 결함이 무엇인지와 실제 파일을 보고합니다. 작고 선별된 표본으로 전체 품질 향상률을 만들지 않습니다. 최종 디자인 선호와 브랜드 적합성에 대한 사용자 평가는 별도로 필요합니다.
