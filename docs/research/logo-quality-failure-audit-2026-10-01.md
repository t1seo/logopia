## 판단

현재 기록에서 가장 분명한 문제는 **알고 있는 디자인 결함이 다음 행동을 바꾸지 않는 제작 과정**입니다. 원본·프롬프트·독립 검토·파일 해시는 잘 남겼지만, 검토에서 고유성 부족이나 설계 이탈을 확인한 후보를 수정·기각·재설계하는 과정으로 연결하지 않았습니다. 설명을 정직하게 붙이는 것과 좋은 후보를 만드는 것은 다른 작업입니다.

이미지 모델의 지시 불이행도 관찰됩니다. 그러나 “AI로는 좋은 로고를 만들 수 없다”, “모델이 업데이트 후 퇴화했다”, “0.9.0 코드가 미적 퇴화를 일으켰다”는 결론은 이 자료로 입증할 수 없습니다. 우선 수정할 수 있는 부분은 브랜드의 고정 결정을 지키고, 서로 다른 설계를 탐색하고, 실제 원본에 대한 비판을 다음 제작 행동에 연결하는 스킬·실행 구조입니다.

이 문서는 기존 기록과 이미지를 읽은 감사 결과이며 새 이미지 생성, 이미지 편집, 사용자 선호 평가, 상표 조사 또는 현재 브라우저 화면 검사를 수행한 기록이 아닙니다. 다른 에이전트의 동시 작업은 수정하지 않았습니다.

## 고정된 서체가 탐색 범위에서 빠진 문제

[브랜드 조사](hail-mary-identity-redesign-2026-10-01.md)는 현재 계약의 Inter와 과거 Instrument Serif를 구분하고 있습니다. 그러나 round2는 자주색 세리프·주홍 워드마크 등 새 레터링을 주요 방향으로 삼았습니다. 이 단계에서 사용자가 “서체는 이미 확정됐으므로 심볼만”이라고 범위를 바로잡아야 했습니다.

이것을 사용자가 아직 하지 않은 명시적 지시를 고의로 무시한 일로 표현해서는 안 됩니다. 다만 확인한 현행 브랜드 자산과 새로 탐색 가능한 영역을 별도 보존하지 못한 것은 분명한 절차 문제입니다. 현재는 사용자가 명확히 범위를 정했으므로 이후 연구·생성·편집에서 **글자 없는 심볼만 생성하고 확정 서체는 변경하지 않는 조건**이 우선해야 합니다. 이를 다시 질문할 필요는 없습니다.

## 현재의 검토가 충분하지 않은 이유

`VisualReview`에는 철자, 구성, 작은 크기, 보존, 배경의 다섯 boolean과 자유 메모가 있습니다. 이는 납품 검사의 일부이지, 디자인이 왜 약한지와 다음에 무엇을 할지 결정하는 제작 루프가 아닙니다. 현재 기록은 승인되지 않은 후보를 승인된 것처럼 내보내지는 않았지만, 리뷰에서 “고유성 미확보”를 확인한 뒤에도 세 장의 비교 페이지를 만드는 단계에서 제작이 끝났습니다.

검토자가 점수를 매기거나 “premium”이라고 말하는 것만 추가해서는 해결되지 않습니다. 그 판단이 실제 이미지의 어느 부분에 관한 것인지, 무엇을 유지하고 바꿀 것인지, 국소 수정으로 가능한지 아니면 방향을 버려야 하는지, 다음 결과에서 무엇을 다시 볼지를 남겨야 합니다. 검토에 필요한 화면이나 파일이 없으면 `uninspected`로 남겨야 하며, 검사가 안 된 항목을 통과로 바꿔서는 안 됩니다.

## 필요한 최소 하네스

하네스의 역할은 좋은 디자인을 자동 판별했다고 가장하는 것이 아니라 **약한 결과가 설명만 붙은 채 다음 단계로 넘어가지 않도록 제작 결정을 기록하고 실행하는 것**입니다. 아래는 구현 담당자가 검증 가능한 최소 계약입니다.

1. **프로젝트 계약:** 목적·사용처·대상, 기존 자산, 고정 결정, 탐색 가능 영역, 제외 영역을 출처와 함께 저장합니다. Hail Mary에서는 심볼만, 확정 서체 유지, 기존 공식 자산 무단 교체 금지가 바로 적용됩니다. 사용자 수정은 버전을 올려 이후 실행의 기준으로 삼습니다.
2. **방향 카드:** 방향마다 브랜드 근거, 설명 없이 보이는 첫 형태, 다른 방향과의 구조적 차이, 실패하면 버릴 이유를 짧게 기록합니다. 색만 바꾼 도형·서체를 별도 아이디어로 세지 않습니다. 설명을 위해 모든 사업 특징을 한 기호에 넣지도 않습니다.
3. **검토할 실제 자료:** artifact ID·해시·세션/리비전·실제 제출 프롬프트를 묶습니다. 원본 보기와 지정 사용 크기 보기는 별도 증거로 남깁니다. 작은 크기 CSS를 작성한 것만으로 실제로 봤다고 기록하지 않습니다.
4. **구체적 비평:** 조건 준수와 디자인 판단을 분리합니다. 실제 관찰, 해당 위치/크기, 문제의 영향, 불확실성을 남기고 기각 가능한 판단을 허용합니다. 작성자와 다른 검토자가 실제 원본을 보면 유용하지만, 별도 에이전트라는 사실 자체가 전문성이나 정답을 보증하지 않습니다.
5. **다음 행동:** `refine`은 좋은 방향의 국소 결함, `reframe`은 방향의 구조적 문제, `reject`는 계속 발전시킬 근거가 없는 후보, `candidate`는 비교를 위해 남길 후보에 사용합니다. 이 명칭들은 제안이며 구현된 API라고 주장하지 않습니다. 어느 경우도 사용자 승인이나 납품 승인과 같지 않습니다.
6. **편집 부모와 비교:** `refine`에는 실제 부모, 유지 항목, 바꿀 항목, 확인 기준을 요구합니다. 자식에서는 같은 관찰 지점을 다시 비교하고 개선/변화 없음/악화/미검토를 남깁니다. 실패한 편집도 원본과 함께 보존합니다.
7. **호출 예산과 중단:** 사용자 지정 수량과 예산이 우선입니다. 품질 루프를 위임받은 경우 최초 탐색과 후속 수정·재설계의 제한된 예산을 시작 시 기록합니다. 예산 소진은 `exhausted`이지 성공·승인이 아닙니다. 반복해서 같은 결함이 나오면 새 금지어를 붙여 무한 생성하지 말고 방법 변경 또는 미해결 종료를 기록합니다.
8. **정직한 전달:** 검토 중인 전체 원본은 남기되 추천 후보와 기각·보류 후보를 구분합니다. 후보가 하나도 충분하지 않으면 그대로 말하고 실패 이유와 다음 가능한 설계를 제시합니다. 검토 불가능한 사용 크기나 미생성 SVG를 성과로 주장하지 않습니다.

## 하네스 검증에 사용할 실패 시나리오

| 시나리오 | 필요한 결과 |
| --- | --- |
| 고정 서체가 있는 심볼 프로젝트에서 새 워드마크 방향을 제출함 | 탐색 범위 충돌을 기록하고 이미지 호출 전 수정. 사용자가 폰트 정보를 다시 입력할 필요 없음. |
| G처럼 폴더 인상이 핵심 구조에서 반복되며 검토자도 지적함 | 단순 설명 보강으로 승격하지 않음. `reframe` 또는 `reject` 등 이유 있는 다음 행동이 남음. |
| B처럼 사전 핵심 조건인 단일 연결 형태가 깨짐 | 조건 불이행을 남기고 해당 후보를 통과로 처리하지 않음. 후속 수정은 정확한 부모를 참조. |
| E처럼 국소 수정은 개선됐지만 고유성 문제는 남음 | 국소 개선을 전체 승인으로 전환하지 않음. 미해결 판단과 잔여 예산이 보임. |
| 후보 세 개를 모두 검토했으나 모두 약함 | 강제 우승안 없음. 예산 내 재설계 또는 `exhausted`/미해결 종료 가능. |
| 공식 GUI 검토 도구가 없어 작은 크기 확인 불가 | 파일/HTML 검증과 시각 검증을 구분하고 미검토를 유지. |
| 이미지 호출 결과가 실패하거나 편집 부모가 달라짐 | 실제 실패·불일치를 보존하며 성공 artifact를 만들어 내지 않음. |
| 사용자 “세 개만 한 번 보여 달라” 요청 | 품질 루프가 수량·비용 의도를 무시해 자동으로 늘어나지 않음. |

이번 감사는 실패 자료를 읽은 진단입니다. 위 하네스가 새로운 사용자 선호를 개선한다는 주장은 실제 실행과 후속 평가 뒤에만 할 수 있습니다.
